Security Systems

The SecuritySystems access-control console app, running in your browser. Its own C++ is compiled to WebAssembly with emscripten, over an in-memory disk-model/ made by the repo's setup.sh.

Try it

  1. r to sign up, role a (admin), p (privileged) or u (common user).
  2. A name, then a password with a lower and upper case letter, a digit and a special character: 4 to 26 symbols, at least 8 for an admin, e.g. Secret#2026.
  3. Four security questions and answers. Your RSA keys are made and you land in the shell.
  4. Try the chips below the terminal, then Run again and sign in with l as another role.

Passwords expire after 3 days and RSA keys after 4, checked when you sign in. The monitoring log is checked once a day when the shell starts.

Once you're in the shell, AccessController's thread asks a security question (85%) or the secret function (15%) every minute. Answer on the next line before it asks again, or the account loses a try and the app exits.

The secret function from setup.sh is exp(x * a) with a = 6, so x = ln(f) / 6, to 2 decimals.

Native and shimmed

  • Native: every line of src/ and lib/mathexpr, compiled with emscripten: the layers, password rules, journal and monitoring parsing, chmod rules, FFT arithmetic.
  • Shell: system() and popen() run a small JS shell over the in-memory FS that honours the permission bits. Each command is its own subshell, as with popen().
  • openssl: genrsa, rsa, pkeyutl and prime in JS BigInt, PKCS#1 v1.5 like OpenSSL. The 8192-bit admin keypair comes from the real setup.sh at build time; keys made in the browser are 2048-bit to stay fast.
  • Thread: no wasm threads on GitHub Pages, so std::thread runs as an emscripten fiber that wakes while the app waits for input.
  • Disk: kept between runs in this tab.
The app runs in a Web Worker, compiled from src/ with a small web shim. Nothing leaves your browser. DichES
